# Requirement 10 – Comparison Document for Nia

## Blue/Green Deployment versus Container-Based Deployment

This project evaluated two approaches for delivering the KijaniKiosk Payments service: a blue/green deployment running directly on virtual machines and a container-based deployment running on Kubernetes. Both approaches improve service reliability compared with deploying directly onto a single running application, but they solve different operational problems. The blue/green deployment focuses on reducing deployment risk by keeping two complete environments available, while the container approach standardizes application packaging and enables automated orchestration.

The blue/green deployment demonstrated that software updates can be introduced without interrupting customer traffic. During deployment, the new version is prepared separately while customers continue using the existing version. Traffic is only redirected after the new version passes health verification. When a simulated application failure was introduced, the monitoring process detected the problem automatically and completed a rollback in **27 seconds**, restoring customers to the previous healthy version without requiring manual intervention. This provides confidence that software releases can be reversed quickly if unexpected issues appear after deployment.

The container approach addresses a different challenge. Instead of depending on differences between servers, the application is packaged together with everything it requires to run. This produces a consistent execution environment regardless of where the application is deployed. The production image created during this project was reduced from a **181 MB** single-stage image to a **45 MB** production image, representing an approximate **136 MB reduction (about 75%)**. A smaller image downloads more quickly, consumes less storage, and reduces deployment time, especially when multiple application instances must be started.

Another important advantage of Kubernetes is automated recovery. During testing, one running application instance was deliberately deleted. Kubernetes detected the missing instance and automatically created a replacement. The complete recovery process took **58 seconds**, demonstrating that the platform can restore application capacity without administrator intervention. Unlike blue/green deployment, which focuses primarily on safe software releases and rollbacks, Kubernetes continuously monitors the desired application state and works to maintain it automatically.

Both approaches contribute to service availability, but they operate at different layers. Blue/green deployment minimizes deployment risk by ensuring that a previously working version remains immediately available if a new release fails. Kubernetes improves operational resilience by replacing failed application instances automatically and maintaining the required number of running replicas. Together they provide complementary protections against different classes of operational failures.

| Concern                  | Blue/Green Approach                                                                                                                                                                  | Container Approach                                                                                                                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Deployment mechanism** | Two complete environments are maintained. A new release is deployed to the inactive environment, verified, and then customer traffic is redirected only after successful validation. | The application is packaged as a versioned container image and deployed as replicated workloads. Every instance runs from the same immutable image, providing consistent behaviour across the cluster. |
| **Rollback mechanism**   | Traffic is redirected back to the previously healthy environment. During testing, the automated rollback completed in **27 seconds** after a simulated failure.                      | Previous container image versions remain available and can be redeployed when necessary. Rolling updates also allow workloads to be replaced gradually while maintaining service availability.         |
| **Failure recovery**     | Relies on monitoring to detect unhealthy deployments and redirect customer traffic to the stable environment. The inactive environment provides immediate recovery capability.       | Kubernetes continuously monitors workloads and automatically recreates failed application instances. The measured recovery time during testing was **58 seconds**.                                     |
| **Scaling**              | Scaling generally requires preparing additional servers or virtual machines and manually distributing traffic between them.                                                          | Replica counts can be increased or decreased declaratively, allowing the platform to manage multiple identical application instances automatically.                                                    |

Although the container-based approach provides significant operational improvements, it does not solve every production concern. Business continuity still depends on well-designed monitoring, backup strategies, security controls, and application quality. Kubernetes can automatically restart failed workloads, but it cannot correct software defects or prevent faulty business logic from being deployed. The next stage of the platform builds on this foundation by expanding orchestration capabilities, enabling more sophisticated deployment strategies, stronger resilience, improved scalability, and increasingly automated operational management while continuing to support reliable software delivery.
